# botmaker-catalog

The list of published BotMaker bots and plugins. **Checked by a machine, merged by a machine — never a security
claim.**

A bot is a Java program and a plugin runs inside Studio's own process. Every check this repository runs asks
whether an entry *works* and whether its author *controls* the repository it names. None of them asks whether
the code is *safe*, and none of them could. Run a bot or a plugin the way you would run any other program
somebody wrote. Studio shows each entry's rank (admin, trusted, community) and asks before it first loads a
community plugin on a computer.

## Publishing

Run in the bot's or the plugin's folder, on a clean tree pushed to GitHub:

```bash
botmaker bot publish            # the next patch release, then the pull request listing it
botmaker plugin publish minor   # patch (the default), minor or major; --tag v1.2.0 names it exactly
botmaker plugin publish --dry-run                  # the checks and the entry, nothing tagged
botmaker bot unpublish --repo me/my-bot [--release v1.0.0]   # the pull request removing the entry, or one release
botmaker plugin unpublish --repo me/my-plugin [--release v0.3.0]
botmaker bot yank --repo me/my-bot --release v1.0.0 --reason "crashes on start"   # --undo lists it again
botmaker plugin yank --repo me/my-plugin --release v0.3.0 --reason "…"
```

A yanked release stays in the entry with its reason: Studio no longer offers it, and tells whoever is on it why.

Studio's Publish does the same for a bot. Each command runs this repository's checks on your machine first, then
tags and releases, then opens one pull request changing one file, which is **merged automatically** when the same
checks pass here. The first publish creates the entry; every later one appends its release, and the earlier ones
stay listed. Install the CLI from [botmaker-cli](https://github.com/BotMakerDev/botmaker-cli).

## Layout

```
bots/<owner>__<repo>.json   { "repo": "owner/name", "releases": [{ "tag": "v1.2.0", "commit": "<sha>",
                                                                  "bmkSha256": "<hex>" }] },
                            optionally "detached": true; either kind optionally "formerly": ["old/slug", …],
                            and a release optionally "yanked": { "reason": "…", "at": "<ISO-8601 instant>" }
plugins/<owner>__<repo>.json { "repo": "owner/name",
                              "releases": [{ "tag": "v0.3.0", "commit": "<sha>",
                                             "jarSha256": "<hex>", "pomSha256": "<hex>" }] }
advisories/BMA-<year>-<NNNN>.json  { "id", "repo", "releases": [tag, …], "severity": "low|medium|high|critical",
                            "summary", "url"?, "published": "YYYY-MM-DD", "withdrawn"?: "why" }; an admin's only
publishers.json             ranks, by GitHub account id; changed by an admin's pull request only
schema/                     JSON Schema (2020-12) of an entry, an advisory and catalog.json: their shape, for
                            editors and other readers; the check below is the authority
catalog.json                GENERATED by index.yml, for the website and other readers. Never edit it
catalog.signed.json         GENERATED beside it: { "payload": base64(catalog.json), "key": "<id>", "signature": … },
                            Ed25519; the only file Studio reads, and only once the signature verifies
tools/                      resolve-cli.sh (the cli's newest release), entry-facts.sh, sign-catalog.sh,
                            new-signing-key.sh (makes the key; its secret CATALOG_SIGNING_KEY is index.yml's)
```

An entry holds only what its author decides: which repository, which releases. `releases` keeps every release the
catalog approved, oldest first; `catalog.json` lists them newest first. Each release is **pinned**: the commit its
tag pointed at when it was approved and, for a plugin, the sha256 of the jar and the pom JitPack served then. A tag
moved or a jar rebuilt afterwards no longer matches, and Studio refuses it. Everything else in `catalog.json`
(name, description, topics, stars, the fork's parent, a plugin's contract version, a bot's plugins, each release's
`publishedAt`, an entry's `updatedAt`, a bot release's `.bmk` `downloads` and its pom's `botmaker.platforms`) is read
from GitHub and from the pom at each pinned commit, as data, by `index.yml`. The index also notices a repository
GitHub renamed or transferred and opens the pull request moving its entry.

`index.yml` signs what it writes: `catalog.signed.json` carries `catalog.json`'s bytes and their Ed25519 signature,
made with the secret `CATALOG_SIGNING_KEY`. Studio checks it against the public keys its core ships and keeps the
last catalog that verified; a file that fails is ignored, never cached.

Every entry's file joins owner and repository with `__`, since a GitHub login holds no underscore, so git keeps
one file per repository. A plugin has no id of its own (since 2026-10-27): its pom's `groupId:artifactId`, which
JitPack serves as `com.github.<owner>:<repo>`, is the plugin.

## The check

`validate.yml` resolves `com.github.BotMakerDev:botmaker-cli` at its newest GitHub Release and runs `com.botmaker.cli.catalog.EntryGate`. A pull request passes when:

1. it changes exactly one entry file, added, changed or removed — or moves one after GitHub renamed or transferred
   its repository: the old file gone, the new one with `repo` the new slug and the old one appended to
   `formerly`, both slugs one repository on GitHub (the nightly index makes this move itself);
2. the file's name is what its content names, the JSON is the schema above (`schema/entry.json`), and the change
   creates the entry with one release, appends one release, removes some releases (the rest kept in order), sets a
   bot's `detached`, or yanks or unyanks one release — a yank's reason 1 to 300 characters, its `at` within a day
   of the check; an approved release is otherwise never edited or reordered;
3. its author made the GitHub Release it approves (or, for a release made by an Action, owns the repository);
4. an existing entry changes or goes only by whoever controls the repository the catalog holds today;
5. the approved release is published, not a draft or a prerelease, and its tag points at the pinned commit;

(A security advisory, `advisories/BMA-<year>-<NNNN>.json` (`schema/advisory.json`), is a pull request of its own:
an admin files it with `botmaker advisory new --repo <slug> --release <tag>[,…] --severity <level> --summary "…"`,
then may only append releases to it (`advisory extend`) or withdraw it with a reason (`advisory withdraw`). It is
never deleted. Ids run in sequence per year, `repo` is an entry's slug or one of its `formerly`, and every tag is an
approved release. `catalog.json` lists the advisories not withdrawn, and Studio refuses to load or run a named
release until its user chooses *Run anyway* for that release on that computer.)

and, on the approved release only, for a bot: its pom at the pinned commit declares a catalog plugin at a released
version, it compiles, and it has a `main`; for a plugin: `botmaker plugin validate`'s checks pass, the jar's pom
declares the plugin as the entry's coordinate, and JitPack serves the coordinate with a jar and pom that hash to the pins.

## Ranks

`publishers.json` lists GitHub account ids (users or organisations) as `admin` or `trusted`; everyone else is
community. An entry takes its repository's current owner's rank, so a fork is its owner's and a transferred
repository takes the new owner's. A pull request that changes `publishers.json` alone passes the check only when
an admin opened it (by account id in the current file), keeps at least one admin and lists no account twice; it
is then merged like an entry. An admin may also change or remove anyone's entry by pull request.
